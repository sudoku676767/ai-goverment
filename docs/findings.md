# 实测记录

## 2026-10-12 · 第一次真实运行：干净的 DeepSeek Harness 基线

**环境**

- 主机：Ubuntu 26.04，黑匣子监听 VMware NAT 网卡地址
- 被测：Win10 虚拟机里的 DeepSeek Harness 桌面版，无第三方插件
- 模型：DeepSeek-V4-Flash，经 OpenAI 兼容中转站调用
- 任务：“在工作区创建一个 hello.py，打印 hello，然后运行它”

**结果**

- 日志 23 条记录，哈希链完整。
- 黑匣子统计输入 31,811、输出 511 token；dsh 界面显示 32.1K，两边吻合。
- agent 用了 4 轮：`glob` 查看工作区 → `write` 写文件 → `pwsh` 运行 → 结束。无重复调用，无报错。
- 每轮输入约 7.6K 到 8.1K token，输出只有 60 到 240。**98% 的 token 是输入，主要是每轮重发的系统提示和工具定义。**
- 从第 2 轮起约 90% 的输入命中缓存，实际费用远低于 token 总数看上去的样子。

**发现：会话标题生成的额度被思考吃光**

dsh 在主任务之外发了一个起标题的请求，`max_tokens` 只有 64。DeepSeek-V4-Flash 是思考型模型，64 个 token 全部用在了推理上，正文为空，被 `length` 截断。标题生成失败后，界面上的标题退回为截断的原话（“在工作区创建一个hello.py,打印h”）。

从界面上只能看到“标题有点怪”；只有看 API 记录才能找到原因。修复方向：给标题请求更大的额度，或对它关闭思考。

**意义**

这是后续插件对照的基线：最简单的任务，固定开销约每轮 7.6K token，4 轮完成。装上插件后跟它比，就能看出插件给每轮增加了多少负担、路径有没有变长。
